# CrossApp

Наскрізний проект з крос-платформного програмування.

Предметна область: Замовлення.

Сутності:
- Customer — клієнт
- Product — товар
- Order — замовлення
- OrderLine — рядок замовлення

Призначення: оформлення замовлень і підрахунок сум.

## Запуск

```bash
dotnet build
dotnet run --project src/Cli
```

## Середовище

.NET SDK 10.0  
macOS 14.6  
RID: osx-arm64

## Лабораторна робота 3

У лабораторній роботі реалізовано імпорт даних для домену «Замовлення».

### Формат CSV

Файл використовує роздільник `;`.

Формат:

```text
id;name;price
```

Приклад:

```text
F-001;Тумба приліжкова Nord;1890.00
```

Ціна зчитується через `decimal.TryParse` з `CultureInfo.InvariantCulture`.

Пошкоджені рядки не зупиняють імпорт, а додаються до списку помилок разом із номером рядка.

### Підтримувані формати

* `.csv` — `ProductCsvImporter`
* `.json` — `ProductJsonImporter`

Вибір імпортера виконується за розширенням файлу через `switch expression`.

### Додаткові завдання

Реалізовано:

* імпорт даних із JSON;
* вибір між CSV та JSON;
* розпізнавання різнорідних рядків за префіксом `P` / `W`;
* статистику імпорту: загальна кількість записів, кількість прийнятих і пропущених записів та відсоток помилок.

### Приклади запуску

```bash
dotnet run --project src/Cli
dotnet run --project src/Cli -- data/sample-valid.csv
dotnet run --project src/Cli -- data/sample.json
dotnet run --project src/Cli -- --mixed data/mixed-sample.txt
dotnet run --project src/Cli -- data/no-file.csv
```
## Лабораторна робота 4

У лабораторній роботі реалізовано доменну модель для предметної області «Замовлення меблів».

### Основні сутності

Реалізовано такі сутності:

* `Order` — замовлення;
* `OrderLine` — окремий товар у замовленні;
* `Product` — товар.

Список товарів у `Order` зберігається у приватному `List<OrderLine>`, а назовні передається як `IReadOnlyList<OrderLine>`.

### Інваріанти

У програмі реалізовано перевірки, які не дозволяють створити або перевести об'єкт у некоректний стан.

Основні правила:

* ID замовлення та клієнта не можуть бути порожніми;
* ID і назва товару не можуть бути порожніми;
* ціна товару не може бути від'ємною;
* кількість товару повинна бути більшою за 0;
* порожнє замовлення не можна підтвердити;
* після підтвердження до замовлення не можна додавати нові товари;
* недопустимі переходи між станами замовлення заборонені.

Для некоректних аргументів використовуються `ArgumentException` та `ArgumentOutOfRangeException`, а для операцій, недопустимих у поточному стані, — `InvalidOperationException`.

### DTO

Для перетворення між DTO та доменними сутностями використовуються методи:

* `ToDto()` — перетворення сутності у DTO;
* `FromDto()` — відновлення сутності з DTO.

Під час `FromDto()` дані повторно проходять усі доменні перевірки.

### Додаткові завдання

Реалізовано:

* перетворення `ImportResult<ProductDto>` з лабораторної роботи №3 у доменні сутності з окремим списком помилок;
* інваріант між `Order` та `Product`: недоступний товар не можна додати до замовлення;
* `enum OrderStatus` зі станами `Draft`, `Confirmed`, `Cancelled`;
* перевірку допустимих переходів між станами через `switch expression`.

### Приклад запуску

```bash
dotnet run --project src/Cli -- --lab4
```

У консолі демонструються успішний сценарій роботи, порушення інваріантів та виконання додаткових завдань.

## Лабораторна робота 5

У лабораторній роботі реалізовано абстракцію сховища та сервісний шар для предметної області «Замовлення меблів».

### Абстракція сховища

Створено інтерфейс `IOrderStore`, який містить основні операції:

- `List()` — отримання списку замовлень;
- `GetById()` — пошук замовлення за ідентифікатором;
- `Add()` — додавання;
- `Update()` — оновлення;
- `Remove()` — видалення.

Реалізовано два основні сховища:

- `InMemoryOrderStore` — зберігає дані в оперативній пам'яті;
- `FileOrderStore` — зберігає замовлення у JSON-файлі.

Для файлового сховища сутності перетворюються в DTO через `ToDto()`, а при читанні відновлюються через `FromDto()`.

### Сервісний шар

Клас `OrderService` залежить від інтерфейсу `IOrderStore`. Конкретне сховище передається через конструктор.

Сервіс підтримує створення замовлення, додавання товарів, підтвердження та скасування замовлення, пошук, отримання списку і видалення.

### Вибір сховища

За замовчуванням використовується `InMemoryOrderStore`:

```bash
dotnet run --project src/Cli
```

Файлове сховище:

```bash
dotnet run --project src/Cli -- --file
```

### Додаткові завдання

1. Реалізовано `CachingOrderStore` як декоратор над `IOrderStore`.
2. Реалізовано пошук замовлень через `Func<Order, bool>`.
3. Реалізовано `StoreFactory`, яка вибирає потрібну реалізацію сховища.

Запуск з кешуванням:

```bash
dotnet run --project src/Cli -- --cache
```

Файлове сховище разом із кешуванням:

```bash
dotnet run --project src/Cli -- --file --cache
```

## Лабораторна робота №6. Доменні події, делегати Action/Func, лямбди

**Мета роботи:** реалізувати механізм сповіщення про зміни стану замовлень за допомогою подій, делегатів та лямбда-виразів, забезпечивши незалежність доменної логіки від способу обробки повідомлень.

### Реалізація

У проєкті CrossApp для предметної області «Замовлення меблів» реалізовано три типи доменних подій:

- `OrderCreated` — створення замовлення.
- `LineAdded` — додавання позиції до замовлення.
- `OrderConfirmed` — підтвердження замовлення.

Створено перелік `OrderChangeKind` і клас `OrderChangedEventArgs`, який містить `OrderId`, `Kind`, `LinesCount`, `Total` та `At`.

У класі `OrderService` оголошено подію `Changed` типу `EventHandler<OrderChangedEventArgs>` і метод `OnChanged()`, який викликає підписників через `?.Invoke()` після успішної зміни стану.

У `Program.cs` реалізовано два підписники:

1. Локальний метод, який виводить інформацію в консоль і записує її до `logs/app.log`.
2. Лямбда-вираз, який підраховує кількість подій через замикання.

Продемонстровано підписку через `+=` і відписку через `-=`. Після відписки першого обробника лічильник продовжує працювати, але нові повідомлення в `app.log` не записуються.

Для пошуку замовлень використано делегат `Func<Order, bool>`.

### Перевірка роботи

Під час запуску отримано чотири події: створення замовлення, два додавання позицій і підтвердження.

Після відписки першого обробника лічильник збільшився до п'яти, а кількість записів в `app.log` залишилася чотири.

Перевірено сценарії відмови:

- Підтвердження неіснуючого замовлення.
- Спроба додавання товару до замовлення у стані `Confirmed`.

В обох випадках операція завершилася помилкою, а нова подія не виникла.

Перевірено, що у вихідному коді `Core` немає прямих звернень до консолі та журналів.

### Додаткове завдання №1. INotificationSink та ручний DI

Створено інтерфейс `INotificationSink` і дві його реалізації: `ConsoleSink` для виведення повідомлень у консоль та `FileSink` для запису у файл.

Об'єкт обробника передається до `OrderService` через конструктор, що демонструє ручне Dependency Injection.

Перевірено роботу обох реалізацій. Файл `sink.log` містить п'ять повідомлень, включно з операцією після відписки обробника події `Changed`.

### Додаткове завдання №2. Action<string>

Реалізовано метод імпорту замовлень із параметром `Action<string> onSkipped`.

Якщо рядок має неправильний формат, метод викликає переданий делегат для повідомлення про пропуск.

Під час перевірки успішно імпортовано два замовлення та пропущено два некоректні рядки.

```bash
dotnet run --project src/Cli -- --lab6
```

### Результат

У лабораторній роботі реалізовано доменні події, два підписники, лямбда-вираз із замиканням, механізм відписки, пошук через `Func<Order, bool>` та логування.

Також виконано обидва додаткові завдання: ручне впровадження `INotificationSink` та використання `Action<string>` для повідомлень під час імпорту.

Програма успішно пройшла перевірку основних сценаріїв та обробки помилок.
