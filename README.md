# CrossApp

Наскрізний проект з крос-платформного програмування.

Предметна область: Замовлення.

Сутності:
- Customer — клієнт
- Product — товар
- Order — замовлення
- OrderLine — рядок замовлення

Призначення: оформлення замовлень і підрахунок сум.

## Запуск

```bash
dotnet build
dotnet run --project src/Cli
```

## Середовище

.NET SDK 10.0  
macOS 14.6  
RID: osx-arm64

### Формат CSV

Файл використовує роздільник `;`.

Формат:

```text
id;name;price
```

Приклад:

```text
F-001;Тумба приліжкова Nord;1890.00
```

Ціна зчитується через `decimal.TryParse` з `CultureInfo.InvariantCulture`.

Пошкоджені рядки не зупиняють імпорт, а додаються до списку помилок разом із номером рядка.

* `.json` — `ProductJsonImporter`

Вибір імпортера виконується за розширенням файлу через `switch expression`.

### Додаткові завдання

* статистику імпорту: загальна кількість записів, кількість прийнятих і пропущених записів та відсоток помилок.

## Лабораторна робота 4

У лабораторній роботі реалізовано доменну модель для предметної області «Замовлення меблів».

### Основні сутності

Реалізовано такі сутності:

* `Order` — замовлення;
* `OrderLine` — окремий товар у замовленні;
* `Product` — товар.

Список товарів у `Order` зберігається у приватному `List<OrderLine>`, а назовні передається як `IReadOnlyList<OrderLine>`.

### Інваріанти

У програмі реалізовано перевірки, які не дозволяють створити або перевести об'єкт у некоректний стан.

Основні правила:

* ID замовлення та клієнта не можуть бути порожніми;
* ID і назва товару не можуть бути порожніми;
* ціна товару не може бути від'ємною;
* кількість товару повинна бути більшою за 0;
* порожнє замовлення не можна підтвердити;
* після підтвердження до замовлення не можна додавати нові товари;
* недопустимі переходи між станами замовлення заборонені.

Для некоректних аргументів використовуються `ArgumentException` та `ArgumentOutOfRangeException`, а для операцій, недопустимих у поточному стані, — `InvalidOperationException`.

### DTO

Для перетворення між DTO та доменними сутностями використовуються методи:

* `ToDto()` — перетворення сутності у DTO;
* `FromDto()` — відновлення сутності з DTO.

Під час `FromDto()` дані повторно проходять усі доменні перевірки.

### Додаткові завдання

Реалізовано:

* перетворення `ImportResult<ProductDto>` з лабораторної роботи №3 у доменні сутності з окремим списком помилок;
* інваріант між `Order` та `Product`: недоступний товар не можна додати до замовлення;
* `enum OrderStatus` зі станами `Draft`, `Confirmed`, `Cancelled`;
* перевірку допустимих переходів між станами через `switch expression`.

### Приклад запуску

```bash
dotnet run --project src/Cli -- --lab4
```

У консолі демонструються успішний сценарій роботи, порушення інваріантів та виконання додаткових завдань.

## Лабораторна робота №6. Доменні події, делегати Action/Func, лямбди

**Мета роботи:** реалізувати механізм сповіщення про зміни стану замовлень за допомогою подій, делегатів та лямбда-виразів, забезпечивши незалежність доменної логіки від способу обробки повідомлень.

### Реалізація

У проєкті CrossApp для предметної області «Замовлення меблів» реалізовано три типи доменних подій:

- `OrderCreated` — створення замовлення.
- `LineAdded` — додавання позиції до замовлення.
- `OrderConfirmed` — підтвердження замовлення.

Створено перелік `OrderChangeKind` і клас `OrderChangedEventArgs`, який містить `OrderId`, `Kind`, `LinesCount`, `Total` та `At`.

У класі `OrderService` оголошено подію `Changed` типу `EventHandler<OrderChangedEventArgs>` і метод `OnChanged()`, який викликає підписників через `?.Invoke()` після успішної зміни стану.

У `Program.cs` реалізовано два підписники:

1. Локальний метод, який виводить інформацію в консоль і записує її до `logs/app.log`.
2. Лямбда-вираз, який підраховує кількість подій через замикання.

Продемонстровано підписку через `+=` і відписку через `-=`. Після відписки першого обробника лічильник продовжує працювати, але нові повідомлення в `app.log` не записуються.

Для пошуку замовлень використано делегат `Func<Order, bool>`.

### Перевірка роботи

Під час запуску отримано чотири події: створення замовлення, два додавання позицій і підтвердження.

Після відписки першого обробника лічильник збільшився до п'яти, а кількість записів в `app.log` залишилася чотири.

Перевірено сценарії відмови:

- Підтвердження неіснуючого замовлення.
- Спроба додавання товару до замовлення у стані `Confirmed`.

В обох випадках операція завершилася помилкою, а нова подія не виникла.

Перевірено, що у вихідному коді `Core` немає прямих звернень до консолі та журналів.

### Додаткове завдання №1. INotificationSink та ручний DI

Створено інтерфейс `INotificationSink` і дві його реалізації: `ConsoleSink` для виведення повідомлень у консоль та `FileSink` для запису у файл.

Об'єкт обробника передається до `OrderService` через конструктор, що демонструє ручне Dependency Injection.

Перевірено роботу обох реалізацій. Файл `sink.log` містить п'ять повідомлень, включно з операцією після відписки обробника події `Changed`.

### Додаткове завдання №2. Action<string>

Якщо рядок має неправильний формат, метод викликає переданий делегат для повідомлення про пропуск.

Під час перевірки успішно імпортовано два замовлення та пропущено два некоректні рядки.

## Лабораторна робота №7. Звіти через LINQ: фільтри, проєкції, групування, топ-N, агрегати

**Мета роботи:** навчитися використовувати LINQ to Objects для обробки колекцій, реалізувати звіти з фільтрацією, сортуванням, групуванням та агрегуванням даних, а також дослідити відкладене виконання запитів.

### Реалізація

У проєкті CrossApp для предметної області «Замовлення меблів» реалізовано систему формування звітів за допомогою LINQ.

У класі `SampleData` створено метод `ReportOrders()`, який формує 20 тестових замовлень для шести клієнтів. Замовлення мають різну вартість і три статуси: `Draft`, `Confirmed`, `Cancelled`.

Для зберігання результатів створено DTO:

- `OrderReportLine` — інформація про замовлення.
- `GroupSummary` — кількість замовлень і загальна сума за статусом.
- `CustomerSummary` — статистика замовлень клієнта.
- `TotalsSummary` — загальна кількість замовлень, сума, середнє значення та максимум.
- `OrderProductSummary` — інформація про товарну позицію після об'єднання замовлень із каталогом.

У папці `Core/Reports` створено клас `ReportService`, який реалізує LINQ-запити незалежно від консольного інтерфейсу.

Реалізовано чотири основні звіти:

1. `TopCustomers()` — топ-5 клієнтів за сумою замовлень. Використано `GroupBy()`, `Count()`, `Sum()`, `OrderByDescending()`, `ThenBy()` і `Take()`.
2. `ExpensiveOrders()` — пошук замовлень дорожчих за 5000 грн. Використано фільтрацію через `Where()`, проєкцію `Select()` у DTO та сортування за сумою.
3. `ByStatus()` — групування замовлень за статусом із підрахунком кількості та загальної суми.
4. `Totals()` — обчислення кількості замовлень, загальної суми, середнього значення та максимуму.

Спискові звіти приймають `IEnumerable<Order>` і повертають `IReadOnlyList<DTO>`. Метод `Totals()` повертає один об'єкт `TotalsSummary`.

Для матеріалізації результатів використано `ToList()`. У звітах із сортуванням за сумою передбачено додатковий ключ `ThenBy()`, що забезпечує визначений порядок елементів з однаковими значеннями.

Уся логіка LINQ-звітів розміщена в `Core/Reports`, а виведення результатів виконується в `Cli/Program.cs`.

### Перевірка роботи

Під час тестування отримано такі результати:

- Топ-5 клієнтів сформовано у правильному порядку за сумою замовлень.
- Знайдено 8 замовлень дорожчих за 5000 грн.
- Групування за статусом: 11 замовлень `Draft`, 5 `Confirmed`, 4 `Cancelled`.
- Загальна кількість замовлень — 20.
- Загальна сума — 104700 грн.
- Середня сума замовлення — 5235 грн.
- Максимальна сума замовлення — 12980 грн.

Повторний запуск `report-top` показав однаковий порядок клієнтів та однакові значення результатів. Це підтверджує стабільність сортування для незмінних вхідних даних.

Також перевірено обробку порожнього набору даних командою `report-empty`. Усі спискові звіти повернули порожні результати, а `Totals()` — нульові показники без виникнення винятків.

У методі `Totals()` передбачено перевірку порожнього списку перед викликом `Average()` і `Max()`. Для обчислення середнього використовується тип `decimal`, що дозволяє зберігати дробову частину результату.

### Відкладене виконання LINQ

Для демонстрації відкладеного виконання створено команду `report-deferred`.

У `ReportService` реалізовано метод `DeferredExpensiveOrders()`, який формує LINQ-запит із використанням `Where()` і `Select()` без виклику `ToList()`.

Спочатку створено запит для пошуку замовлень дорожчих за 5000 грн. Перший виклик `Count()` повернув 8. Після додавання нового замовлення до вихідної колекції повторний виклик повернув 9.

Після збереження результату через `ToList()` початкову колекцію було очищено. Повторне виконання початкового запиту повернуло 0, але збережений список містив 9 елементів.

Отримані результати:

- До додавання замовлення — 8.
- Після додавання замовлення — 9.
- Після очищення джерела — 0.
- Збережений результат `ToList()` — 9.

Таким чином, продемонстровано, що LINQ-запит із `Where()` виконується відкладено та враховує поточний стан джерела під час кожного повторного перебору. Метод `ToList()` матеріалізує результат і створює окремий список, який не залежить від подальших змін початкової колекції.

### Додаткове завдання №1. Join()

Створено метод `ReportProducts()`, який формує каталог із п'яти меблевих товарів.

У `ReportService` реалізовано метод `JoinOrdersProducts()`, який об'єднує позиції замовлень із каталогом за полями `OrderLine.ProductId` та `Product.Id`.

Для отримання позицій із замовлень використано `SelectMany()`, після чого оператор `Join()` зіставляє їх із відповідними товарами.

Для результатів створено DTO `OrderProductSummary`, який містить номер замовлення, назву товару, кількість і вартість.

Під час перевірки успішно об'єднано 20 товарних позицій. Усі результати відображено командою `report-join`.

### Додаткове завдання №2. Власний метод розширення

Створено клас `OrderReportExtensions` із власним методом розширення `WithMinimumTotal()` для колекції `IEnumerable<Order>`.

Метод використовує `Where()` для пошуку замовлень, сума яких не менша за задане значення.

Власне розширення використано у двох звітах:

1. `MinimumTotalOrders()` — відбір замовлень за мінімальною сумою.
2. `TopCustomers()` — формування топ-N клієнтів із можливістю враховувати лише замовлення від заданої суми.

У методі `TopCustomers()` параметр `minimum` за замовчуванням дорівнює 0, тому стандартний звіт топ-5 клієнтів працює без змін.

Під час запуску `report-extension` знайдено 8 замовлень із сумою від 5000 грн.

### Додаткове завдання №3. Query Syntax

У `ReportService` реалізовано метод `ByStatusQuery()`, який використовує синтаксис LINQ-запитів через `from`, `group ... by ... into`, `orderby` і `select`.

Метод групує замовлення за статусом, визначає кількість елементів у кожній групі та обчислює загальну суму. Результат перетворюється на DTO `GroupSummary`.

Під час запуску `report-query` отримано:

- `Draft` — 11 замовлень, сума 67230 грн.
- `Confirmed` — 5 замовлень, сума 27930 грн.
- `Cancelled` — 4 замовлення, сума 9540 грн.

**Порівняння читабельності синтаксисів**

Було порівняно два способи запису LINQ-запитів: методний синтаксис із використанням `GroupBy()`, `Select()` і `OrderBy()` та синтаксис запитів `from ... group ... into ...`.

Обидва варіанти формують однакові групи, кількість замовлень і загальні суми. Відрізняється лише порядок відображення статусів через різні способи сортування.

Методний синтаксис зручний для послідовного застосування LINQ-операцій, а Query Syntax наочніше показує процес групування даних. Для цього завдання обидва способи є зрозумілими, проте методний синтаксис компактніший і краще поєднується з іншими звітами проєкту.

### Додаткове завдання №4. Stopwatch

За допомогою класу `Stopwatch` виконано порівняння часу формування LINQ-звіту з проміжним `ToList()` та без нього.

Для експерименту згенеровано 100000 тестових замовлень. У кожному варіанті виконується пошук замовлень дорожчих за 5000 грн із подальшим сортуванням і перетворенням у DTO.

Порівнювалися два методи:

1. `ExpensiveOrders()` — формування звіту без проміжного `ToList()`.
2. `ExpensiveOrdersWithToList()` — формування звіту з додатковим `ToList()` усередині LINQ-ланцюжка.

Час генерації тестових даних не включено до вимірювання.

Результати останнього запуску:

- Згенеровано записів — 100000.
- Без проміжного `ToList()` — 60000 записів, 115,20 мс.
- Із проміжним `ToList()` — 60000 записів, 95,17 мс.

Обидва способи повернули однакову кількість записів — 60000, що підтверджує однаковість результатів фільтрації.

У цьому запуску варіант із проміжним `ToList()` виконався швидше. Проте результати вимірювання залежать від умов запуску, оптимізацій середовища .NET і навантаження комп'ютера. Один експеримент не дозволяє зробити універсальний висновок про продуктивність.

### Самоперевірка

Перевірено такі вимоги:

- У `Program.cs` немає викликів `Where()` і `GroupBy()` для формування звітів.
- Два запуски `report-top` повертають однаковий порядок клієнтів.
- Звіти правильно обробляють порожні колекції.
- Для готових звітів використовуються DTO замість передачі доменних об'єктів.
- У `Core/Reports` немає `AsParallel()` та вкладених циклів замість LINQ.
- Для топ-N використовується другий ключ сортування.
- Реалізовано LINQ to Objects без використання PLINQ і LINQ to SQL.

## Лабораторна робота №8 — async/await, скасування та unit-тести

### Мета роботи

Реалізувати асинхронний імпорт рядків замовлення, підтримку кооперативного скасування через `CancellationToken`, обробку доменних винятків та unit-тестування ключової логіки `Core` за допомогою xUnit.

### Реалізація

Для варіанта **«Замовлення»** створено інтерфейс `IOrderLineImporter` та клас `JsonOrderLineImporter`.

Для асинхронного читання JSON використовується `FileStream` із параметром `useAsync: true`. Метод `StreamAsync()` використовує `JsonSerializer.DeserializeAsyncEnumerable()` та повертає `IAsyncEnumerable<OrderLineDto>`. Метод `LoadAsync()` формує готовий список, перебираючи записи через `await foreach`.

Метод `OrderService.ImportAsync()` отримує імпортовані рядки, перевіряє `CancellationToken` та додає їх до замовлення через `AddLine()`. Після успішного додавання виникає подія `Changed`.

Асинхронним реалізовано файлове введення-виведення. Перевірка бізнес-правил, зміна стану замовлення та обчислення суми залишилися синхронними.

### Доменні винятки

Для обробки помилок використано:

- `DomainException` — порушення бізнес-правил, наприклад повторне підтвердження замовлення або некоректні дані імпорту.
- `ArgumentException` — некоректні аргументи методів, наприклад порожній ідентифікатор або недопустима кількість товару.
- `OperationCanceledException` — скасування асинхронної операції.

Під час обробки помилкових даних імпорту зберігається початкова причина помилки через `InnerException`.
